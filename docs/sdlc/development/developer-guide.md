<!-- sdlc:auto:start overview -->
TimeTrack Pro is a time and labour management web app (roles, timesheets, approvals, leave, labour rules, reports), generated by the Quorq AI SDLC platform as two apps in one repository. `frontend/` is a Vite 6 + React 19 + TypeScript SPA styled with Tailwind CSS v4 and routed with react-router-dom v7. Its screens (SignIn, Dashboard, Timesheet, Users, Projects) render seeded sample data and do not call the API yet. `frontend/src/lib/api.ts` (`apiFetch`) is the prepared seam for wiring screens to real endpoints. `backend/` is a FastAPI 0.115 service using SQLAlchemy 2.0. It defaults to a local SQLite file (`app.db`) and switches to PostgreSQL 16 when `DATABASE_URL` is set. Tables are created from the models at startup, with no migrations. The backend currently implements `/health`, email/password auth (`/api/auth/login`, `/logout`, `/me`, with argon2 hashing and a JWT-style token) and company labour-rule settings (`GET`/`PUT /api/settings`). Note that the root README still says the backend has only a health check. Pushes to `main` deploy via GitHub Actions: the API image goes to AWS ECR and the frontend to AWS Amplify.
<!-- sdlc:auto:end overview -->

<!-- sdlc:auto:start prerequisites -->
- Node.js 20+ with npm (for the Vite 6 / React 19 frontend)
- Python 3.12 (the version used by backend/Dockerfile)
- Docker with Docker Compose (optional: for the PostgreSQL 16 database in docker-compose.yml and for building the API image)
<!-- sdlc:auto:end prerequisites -->

<!-- sdlc:auto:start setup -->
1. git clone <repo-url> && cd <repo-dir>
2. cd backend && python -m venv .venv && .venv/bin/pip install -r requirements.txt
3. (still in backend/) .venv/bin/uvicorn app.main:app --reload   # API on http://localhost:8000, SQLite ./app.db created automatically
4. Optional, to use Postgres instead of SQLite: from the repo root run `docker compose up -d db`, then start the API with `DATABASE_URL=postgresql+psycopg://app:app@localhost:5432/app .venv/bin/uvicorn app.main:app --reload` from backend/
5. In a second terminal: cd frontend && npm install && npm run dev   # SPA on http://localhost:5173 (the origin the backend allows by default)
<!-- sdlc:auto:end setup -->

<!-- sdlc:auto:start conventions -->
- Backend: one APIRouter per component, each under an `/api/<component>` prefix with a matching tag, registered in main.py via `app.include_router`.
- Backend: dependencies use `Annotated[..., Depends(...)]`. Examples are `get_db` for a per-request session, `get_current_user` for authenticated routes and `require_admin` for admin-only writes.
- Backend: request/response Pydantic v2 models are defined next to their router, e.g. `LoginRequest`/`UserOut` and `SettingsIn`/`SettingsOut`. `SettingsIn` uses strict numeric types and field validators.
- Backend: SQLAlchemy 2.0 typed models (`Mapped`/`mapped_column`) inheriting `app.database.Base`. User IDs are UUID strings. Timestamps use `UTCDateTime`/`utcnow` from services/timeutil and are serialized with `iso_z`.
- Backend: no migrations. `Base.metadata.create_all` runs in the app lifespan, and the code comments say to replace it with Alembic before real data exists.
- Backend: unimplemented generated routes return `schemas.StubResponse` (`status: not_implemented`) instead of raising.
- Backend: login uses a generic 'Invalid email or password' error and a dummy hash, so unknown users and wrong passwords look the same.
- Frontend: the `@/` import alias maps to `src/` (vite.config.ts and tsconfig.json).
- Frontend: one module per screen in `src/screens/`. Routes are declared in App.tsx inside `AppShellLayout`, `/sign-in` sits outside the shell, and unknown paths redirect to `/sign-in`.
- Frontend: styling uses Tailwind v4 classes plus brand CSS variables (`var(--brand-*)`) defined in index.css and brand.ts.
- Frontend: all API calls should go through `apiFetch` in `src/lib/api.ts`. It prefixes `VITE_API_BASE_URL` and sends the session token from localStorage, or the shared secret, as a Bearer header.
- Frontend: TypeScript runs with `strict` but `noImplicitAny` and `strictNullChecks` disabled.
- Frontend: Vitest component tests live beside the components they cover (`src/**/*.test.tsx`). Playwright specs live in `e2e/`.
- Code style is enforced by ESLint and Prettier (frontend) and Ruff (backend). The platform gates on `npm run lint`, so keep it green.
<!-- sdlc:auto:end conventions -->

<!-- sdlc:auto:start troubleshooting -->
| Problem | Solution |
|---|---|
| POST /api/auth/login always returns 401. | No user-creation or seed endpoint exists yet, so the users table starts empty. Insert a `users` row with a lowercase email, `is_active` true and a `password_hash` produced by `argon2.PasswordHasher().hash(...)`. |
| Browser blocks API calls with a CORS error. | The API only allows http://localhost:5173 and http://127.0.0.1:5173 by default. Run the frontend on that port, or set `ALLOWED_ORIGINS` (comma-separated) when starting uvicorn. |
| Frontend screens show the same data regardless of the backend. | This is expected. The screens render seeded sample data. Wire a screen to the API by calling `apiFetch` from `src/lib/api.ts`. It targets `VITE_API_BASE_URL`, which defaults to http://localhost:8000. |
| `pytest` fails with `ModuleNotFoundError: No module named 'app'`. | Run pytest from inside `backend/`, where pytest.ini sets `pythonpath = .`. |
| `npm run test:e2e` cannot start the backend web server. | Playwright launches `backend/.venv/bin/python`. Create that venv and install requirements: `cd backend && python -m venv .venv && .venv/bin/pip install -r requirements.txt`. Run `npm run test:e2e:install` once for Chromium. |
| `npm run build` succeeds but `npm run typecheck` reports errors. | The build does not typecheck. Fix the reported types, often untyped `useState({})` read for named fields, before relying on `tsc`. |
| Model changes do not show up in an existing database. | `create_all` only creates missing tables and never alters existing ones. For local SQLite, delete `backend/app.db` and restart. For data you need to keep, introduce migrations (e.g. Alembic). |
| API fails at startup when using Postgres. | Make sure `docker compose up -d db` is running and healthy, and that `DATABASE_URL` uses the psycopg 3 driver, e.g. `postgresql+psycopg://app:app@localhost:5432/app`. |
| Security issue: the API shared secret is hardcoded in the repository and exposed in the built bundle. | .github/workflows/deploy.yml hardcodes the shared API secret in plain text as `VITE_API_SECRET_KEY` and `NEXT_PUBLIC_API_SECRET_KEY`. Vite inlines `VITE_*` values into the public bundle, so anyone loading the site can read it. Rotate that value, move it to a GitHub Actions secret, and avoid shipping a long-lived shared secret to browsers. Rely on the per-user login token instead. |
<!-- sdlc:auto:end troubleshooting -->
